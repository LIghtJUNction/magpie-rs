## F-01：保留模型选择并说明发现与可服务状态

- 角色/任务：用户保存模型后刷新目录，再在 Agent 选择并实际请求它。
- 证据：[原版 #4343](https://github.com/yetone/magpie/issues/4343) 最初在 0.1.2121 报告 Copilot Enterprise 显式选择被目录过滤；维护者说明 0.1.2659 已纳入修复，[作者确认 0.1.2679 解决并关闭](https://github.com/yetone/magpie/issues/4343#issuecomment-6569262876)。状态 closed/completed，不当成当前上游未修复问题。真实 Enterprise 账户未在本项目验证。
- 另见 [#4851](https://github.com/yetone/magpie/issues/4851)，2026-11-02 为 open、0 评论：WorkBuddy AI 模型可选但请求被账号列表拒绝。原因未经维护者确认；不照搬报告者的实现提案或合并成已确认同一根因。
- 要求：显式选择、发现结果、可服务模型和每模型可用端点保持清楚；刷新失败/目录暂缺不得无声清空选择。只显示实际可服务模型或明确不可用原因及恢复动作，不靠 HTTP 200 探针宣称完整推理可用。不能仅凭 Experimental 字样过滤提供给用户的模型。
- 验收：合成目录先含 a/b，用户选 b；后续目录缺 b、请求返回 403、刷新超时和坏 JSON，保存选择不丢、服务状态准确、错误可操作；Responses 可用而 Chat 不支持时保持端点区分。修复仅在本地复现后登记“已修复”。
- 映射/优先级：REQ-004/016/017/029/034/085；高优先，直接阻断已保存模型的日常使用。

## F-02：流内错误进入失败账务且不自动重播

- 角色/任务：用户通过同协议或跨协议调用流式模型，流开始后收到厂商 error frame。
- 证据：[原版 #4855](https://github.com/yetone/magpie/issues/4855)，2026-11-02 为 open、0 评论，指出插件同协议 passthrough 未采用流内 error 的 code/status，路由与最终请求被记为健康。属于上游报告，当前 Rust 尚待同样 fixture 复现；插件能力本身仍未实现。
- 要求：已发成功 HTTP 头后的显式 error frame 仍是失败终态；保留脱敏的代码、上游状态和操作阶段，最终请求与尝试账务一致。不得因为已经 200 就统计成功，不得在输出首字节后重放到另一上游，不写原始 prompt/密钥。原版自己写出的终止错误也必须保持相同错误归属。
- 验收：本地 SSE fixture 分别在零内容与一段 delta 后返回 error(code=upstream_timeout,status=504)，同协议/转换路径均可辨失败；上游各调用一次、失败账务一次且终结正确；正常终态、无终态断流和客户端取消分别判定。未来插件路由复用同一检查。
- 映射/优先级：REQ-032/033/045/050/059/065；高优先，避免静默成功和重复请求。
