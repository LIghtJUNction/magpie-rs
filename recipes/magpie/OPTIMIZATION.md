# 实现与持续优化合同

本合同由用户“实现本项目配方、Rust版本magpie、建立明确性能指标不断优化”的补充要求产生。先更新配方，再运行递归check、pack和build查看完整提示词；Agent随后实际编写实现、运行验收和测量。Recipkg build本身不执行软件实现。

## 工作顺序

1. 保持93条功能需求，读取全部递归配方。每轮选择可独立验收的完整用户操作，先定义输入、成功/失败结果和涉及的REQ。
2. 基线运行属于用户授权的性能工作范围。使用独立实现目录、隔离配置和本地上游，记录准确的源码/构建/fixture指纹。禁止用真实用户的Agent配置、密钥和会话作为测试输入。
3. 新功能先满足正确性，再用PERFORMANCE.md的固定负载测量；尚不存在的功能记为未实现/未测量，不能用health、空循环或错误响应代替真实转发。
4. 优化前说明瓶颈和预期影响；只改变与该瓶颈相关的实现，保持正确性与负载不变。前后版本交替运行至少5轮，报告每轮及中位数/范围；结果差异落在测量波动内时记为无可测改善。
5. 保留通过功能验收且有证据的改动；性能目标冲突时记录取舍，不能通过删除功能、丢数据、拒绝有效请求或隐瞒错误获得更好数字。
6. 若优化改变了可观察行为、支持平台或预算，先更新对应配方和验收，再重建完整提示词。实现数据与证据改变时更新结果记录，不能覆盖原迁移快照来假称原版已通过。

## 明确的指标定义

| 指标 | 测量边界和单位 | 正确性门槛 |
| --- | --- | --- |
| CLI启动 | 从父进程创建子进程到stdout关闭且成功退出，毫秒；单独记录解析/发现操作 | 退出码、stdout内容和JSON schema全部正确 |
| 服务启动 | 从进程创建到健康检查成功且模型目录实际就绪，毫秒；二者时间分别记录 | 不能以仅监听端口表示Provider可服务 |
| 常驻内存 | 固定稳定窗口内目标进程及其专用子进程RSS/PSS中位数与最大值，MiB | 记录进程树；共享页/子进程不能漏计或重复相加 |
| 请求峰值内存 | 完整负载持续采样的最大RSS/PSS，MiB；记录采样间隔和可能漏峰 | 请求完成数量、成功/失败/拒绝/取消数量明确 |
| 网关额外延迟 | 同一fixture直接调用与经网关调用的首事件/总耗时，毫秒，分别报告p50/p95 | 两侧负载、返回字节、usage和工具调用语义相同 |
| 吞吐 | 成功完成且内容正确的请求数/测量秒数，req/s；有效载荷字节/s | 429、超时、空响应、失败重试不能计为成功 |
| 流式内存 | 保持并发/块速率固定，增加流总时长/总长度，观察峰值与持续增长 | 首块在流结束前交付，取消传播，缓冲不随累计流长度增长 |
| 取消资源回落 | 取消到上游停止、连接/队列释放的时间，毫秒；回落后的RSS/句柄 | 上游计数或连接状态证明实际停止，不只关闭本机UI |
| Usage查询 | 固定1万/100万条数据，分页/筛选/聚合/导出耗时与峰值内存 | 行数、过滤、总计、去重正确；记录索引和冷暖缓存 |
| GPUI交互 | 启动到可操作、输入/滚动事件到下一帧呈现，毫秒；帧时p50/p95 | 实际窗口、正确列表内容、固定分辨率/刷新率/主题 |
| 分发体积 | stripped可执行字节数、完整安装包字节数、依赖/运行时体积 | CLI和GUI分开列，外部JS/模型/库不能静默漏计 |

## 预算与回归门槛

用户没有提供绝对毫秒/MiB/吞吐预算。不能把未经测量的数字写成用户已确认要求。首次真实基线完成后，按设备/OS/运行模式分别提出明确预算并记录其依据；性能报告不得保留只有“快”“小”“尽可能”的结论。

在绝对预算待定阶段也执行明确门槛：有效fixture的错误或内容不符数量为0；不泄漏密钥/正文；并发、等待、缓存、请求体、保留期和输出尺寸均有配置上限，超限行为符合规格；流式缓冲不随已处理总长度无界增加；取消和失败最终释放专属资源。内存/延迟与最近同功能有效基线比较，超过正常轮间波动的恶化必须调查，不能自动接受。

新增功能造成的资源增长应与相同功能的可用实现比较，并单独记录新增成本。不能拿健康检查原型的体积/RSS作为完整产品不可突破的绝对上限。不同设备的指标不直接混为一个通过结果。

## 每轮结果记录

记录：日期、涉及REQ、源码/二进制/fixture散列、OS/CPU/RAM/GPU、工具链与release参数、工作负载与运行命令、采样工具/间隔、冷暖缓存、并发、总时长、请求与有效字节计数、全部错误、逐轮数值、中位数/范围、瓶颈、预算及通过/失败/未测量结论。保留原始机器可读数据和必要日志，日志不含凭据或真实prompt。

## 当前基线和优化结论

2026-10-28 已记录一个 Linux x86_64 CLI/空目录网关实现子集基线，结果、硬件、运行方式和局限见 PERFORMANCE.md 与 EVIDENCE.md。当前测量覆盖每类 CLI 操作 30 次、网关启动 30 次、目录请求 100 次；完整转发、流式、并发、GPUI、Android 和其它系统尚无数据。绝对预算仍未知。

目前没有通过至少5轮前后交替对照证明某项优化带来稳定改善。首次结果只用作后续同硬件、同负载比较的参照；不能把旧二进制与新二进制差值解释成代码优化收益。下一轮应先 profile 实际瓶颈，再选一个已实现且可正确验收的工作负载，保持二进制、fixture、主机和统计方法可比并交替运行。
