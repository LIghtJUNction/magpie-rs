# 原版行为与重建逐项验收

目标是完整重建原版可观察功能，再在不破坏这些功能和用户数据的前提下改进体验、资源占用与平台覆盖。原有 93 条 REQ 和 68 类 Agent 是最低清单；固定原版 0.1.2185 的新增 REQ-105–110 使当前清单扩展为 99 条，仍不是上限。本文件补充执行方法；各递归规格和 ACCEPTANCE.md 的完整合同仍然有效。当前实现、目录、演示截图和单次合成成功都不能缩小范围或证明一比一完成。

## 基线和证据的归属

为每次对照记下原版版本、二进制 SHA-256、操作系统/架构、使用入口、隔离环境、初始完整状态、输入、操作顺序、输出、退出码或 HTTP 状态、完整后置状态及重启结果。分别记录重建版本及二进制/源码提交，保留原始结果、失败和复测；敏感信息使用合成值。界面图像还要记录主题、语言、尺寸、状态及是否为实际窗口。网络或账号不可用时，标为未验证，不能用模拟服务的成功推断真实 Provider、订阅或平台兼容。

现有直接运行的 CLI 基线是 Linux 原版 `magpie 0.1.1948`，二进制 SHA-256 `9aa760cbac67f375a810fcf15b9adf04edcb2cc7de64a9ebb0963da15c1d3eb7`；它的本机包数据库版本与程序自报版本不同，不能用包号替代实际二进制身份。采集条件、原始输出、局限和合成候选样本见 [ORIGINAL_CLI_BEHAVIOR.md](ORIGINAL_CLI_BEHAVIOR.md)。官网截图和文档是公开参考，不证明它们与此二进制同一构建；源码观察、文档陈述、原版实测和重建实测分开标记。

每个功能至少维护以下字段，记录在覆盖表或可追溯证据中：需求编号、用户任务及入口、固定原版和已观察范围、原版未观察项、重建版本、正常/错误/恢复结果、状态持久化、平台与测试数据、证据位置、结果（通过/失败/未运行/不适用及理由）。同一需求跨入口、Agent、协议或平台时要分别记录，不把一个单元的通过填成整项通过。新增观察到的功能继续加入，不因为原表已有 93 项而遗漏。

## 已观察的 CLI 回归样本

以下只约束上述固定原版和 `ORIGINAL_CLI_BEHAVIOR.md` 所述空合成条件，不能推广到真实配置、其他版本或平台。逐字节断言时保留 stdout、stderr、退出码、行尾空格与换行；不要以 trim 后比较冒充字节一致。

REQ-001 对用户 Agent 列表的描述与空环境 `agents` 列出所有支持项的实测存在入口范围上的未决差异：`agents`、`ls` 分别按以下样本对照，其他用户列表仍按 REQ-001 实现并继续验证原版，不能把两条 CLI 结果推断成所有 UI 的规则。详见 `OPEN_QUESTIONS.md`。

1. 空 PATH、合成 `CODEX_HOME` 路径不存在时，`agents` 列出 68 条受支持项且均显示未检测到；`ls` 的 stdout 为空，stderr 是 `magpie: no supported agents found on this machine` 加换行，退出 1。
2. 同条件下分别放入合成可执行文件 `claude`、`codex`、`gemini`，及三者两两/全部组合；`ls` 按已观察顺序列出相应条目、退出 0。未设置 `CODEX_HOME` 时使用默认 `~/.codex/config.toml` 显示路径。只创建空 `~/.codex` 而无 CLI 时，已观察 `ls` 仍返回一条 `CLI not found` 和退出 0。各组合的完整输出及指纹见对应证据，不能只断言行数。
3. 空数据下 `sessions --json` 为数组，`sessions --days 1 --json` 为带汇总的对象，`usage --csv` 是 47 列表头；具体字段和值逐条对照证据。已观察普通查看/版本会生成初始化文件，而帮助不生成；重建若为安全或其他明确理由有意不同，记录差异、用户可见影响及决策，不能悄悄称为字节级一比一。

## 独立重建与发布门槛

先对打包后的完整递归配方做结构检查，再由未读取本项目生成源码或原版实现的独立工作区生成软件。使用合成 fixture 实际执行各级验收，之后才用固定原版做黑盒差异对照。逐项记录缺口、重新补回配方并重新打包；结构检查、能编译、局部测试或一张截图都不是完整重建通过。

分别记录本地编译/合成验收、真实原版对照、目标 OS/CPU 和设备运行、AUR 可见与安装、Release 附件及安装，各状态不能互相替代。Android CLI 与原生 GPUI GUI 分开，固定 GPUI 后端能力不足时该 GUI 项保持未完成。没有足够样本或数字预算时不宣称资源目标通过。版本化早期发布如发生，须明确缺失功能和实际测试边界，不能写成一比一完成。
